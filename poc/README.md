# 工單分流 PoC

讀進 48 筆客服工單，判斷每一封該不該處理、由誰處理、客戶要什麼，然後標記它可以自動回覆還是必須轉真人。

## 執行方式

```bash
cd poc
uv sync
cp .env.example .env        # 填入 GEMINI_API_KEY
uv run python -m triage
```

產出三個檔案：

| 檔案 | 內容 |
|---|---|
| `triage_result.csv` | 48 筆分流結果 |
| `SUMMARY.md` | 執行摘要：類別分佈、需人工比例、資料問題 |
| `drafts.md` | 草稿回覆，個資已還原 |

**沒有金鑰也能跑。** `data/responses/` 裡有每一封工單的模型原始回應（含模型代號、prompt 版本、token 用量）。沒有 `.env` 或沒有 `GEMINI_API_KEY` 時，管線改讀這些檔案，產出完全相同的結果。缺檔的工單不會被略過，而是判定分類失敗、轉真人。

其他用法：

```bash
uv run python -m triage --offset 0 --limit 15   # 只跑前 15 筆
uv run python -m triage --refresh               # 忽略既有回應，重新呼叫 API
uv run python compare.py                        # 跟人工標註比對，列出不一致
uv run python -m unittest discover tests        # 測試，不需要金鑰
```

## 結果

48 筆全數產出，`gemini-3.5-flash-lite`，每筆一次呼叫，平均約 1,450 input token、130 output token。

| 指標 | 數字 |
|---|---|
| 與人工標註一致 | 48 / 48 |
| 轉真人 | 34 / 48（71%） |
| 可自動處理 | 14 / 48（29%） |
| 先送出範本回覆、案件仍進人工 | 24 / 48（50%） |
| 只回收件確認 | 10 / 48（21%） |
| 不回覆自動關單 | 2 / 48（4%） |
| 同時命中多個情境 | 22 / 48（46%） |

情境群組分佈：訂單查詢 35%、知識查詢 29%、不查系統 19%、轉其他單位 10%、不受理 4%、會員系統 2%。

主管的估計是「四成問訂單、三成問產品、兩成要退改」。實際跑出來，訂單相關（含退改）合計 35%、知識類 29%，方向對得上，但退改與客訴的比重比估計高，而且有 10% 根本不是客服該回的信。

**轉真人的 34 筆，全部都命中「情境需人工」這一條。** 其他五條規則在這 48 筆上沒有一筆是單獨生效的，它們是縱深防護不是獨立來源。這件事本身是結論：在訂單 API 與知識庫都還沒到位的前提下，能自動化的範圍由情境本身決定，跟個案的旗標關係不大。

比對用 `uv run python compare.py`，標註在 `data/expected.json`。

**這個 48/48 不是準確率。** 它的意思是「模型的判斷和一位標註者對同一份定義的理解一致」，而那位標註者同時是寫 prompt 的人，樣本只有 48 筆。它能證明的是分類體系的定義夠明確、模型讀得懂；它不能證明分類對業務是對的。要證明後者，需要客服人員在真實工單上標，而且標註者不能是寫規則的人。

迭代過程中改過三次標註，改的依據都是文件定義而不是「模型這樣說」，每一筆都在 `expected.json` 留了 `_note`：

| 工單 | 初標 | 改判 | 依據 |
|---|---|---|---|
| TK-1009 指定郵輪艙位 | `auto` | `human` | 客戶已完成預訂，指定艙位會動到訂單，屬不可逆動作 |
| TK-1045 加購托運行李 | `auto` | `human` | 同上，加購會動到已成立的訂單 |
| TK-1030 網頁標價與結帳不符 | `is_complaint=false` | `true` | 「也沒有說明差在哪」是指公司未交代價差，屬對本公司作為的不滿。初標誤用「語氣不激烈」當判準，而那正是定義裡明文排除的 |

前兩筆讓「不可逆動作」的邊界從「客戶明說要改」擴到「訴求會動到已成立的訂單」，第三筆讓「客訴」的邊界從語氣改回訴求對象。**這三次都是定義沒寫清楚被模型問出來的**，不是模型分錯。

## 資料裡有什麼問題

原始附件是 `.xlsx`，48 筆。前處理修掉的東西都會記在每筆工單的註記裡，`SUMMARY.md` 直接統計。

| 發現 | 處置 |
|---|---|
| `created_at` 是 Excel 序列值（`46195.3847`） | 依 1900 日期系統轉成台北時間。資料範圍 2026-06-22 到 06-27，符合題目說的「近一週」 |
| 管道欄位混用 `email` 與 `表單` | 正規化成 `email` / `form` |
| 全形數字（`３月２８日`） | 轉半形。全形標點是中文的正確寫法，不動 |
| HTML 換行標籤與郵件簽名檔（TK-1020） | 移除 |
| 內文極短，看不出訴求（TK-1024、TK-1033、TK-1041） | 保留，交給分類判斷；`test_noise` 與 `ask_clarification` 就是給這些用的 |
| 博弈廣告（TK-1008）、測試資料（TK-1041） | 判為不受理，自動關單 |
| 非客戶來信：供應商、應徵、業配、媒體、企業包團 | 判為 `non_support`，轉其他單位，客服不回 |
| 重度個資（TK-1023 身分證、手機、銀行帳號） | 本機抽取後假名化，見下 |
| 同一位寄件者的重複來信（TK-1013 與 TK-1031） | **不自動合併**。合併需要 thread id 或可靠的客戶識別，姓名已假名化，不是可靠鍵。在摘要裡點名，交給人工判斷 |

## 設計

### 三層判定，一次呼叫

```
工單 → 前處理 → 本機抽個資 → 假名化 → ┐
                                      ├→ Gemini（一次呼叫，回傳三層 + 旗標）
                                      ┘
   → 驗證與對帳 → 六條分流規則 → 草稿範本 → 還原個資 → 落地
```

1. **受理判定** `accept` / `reject`
2. **承辦歸屬** `support` / `referral` / `not_applicable`
3. **服務情境** 17 個，可複選

三層都由模型填，程式再拿情境目錄裡登記的值去核對它自己填的前兩層。對不上就當分類失敗轉真人，不修補。理由見 `../docs/adr/0003-*`。

情境定義在 `triage/catalog.py`，是這個 PoC 唯一的情境真值來源：送給模型的判斷說明、輸出 schema 的值域、下游工具綁定、回覆範本全部由它生成。新增一個情境只改那一個檔案。

### 為什麼用 LLM 而不是規則或傳統 ML

規則表在這個題目上會立刻失效：TK-1011 是客訴信，裡面出現「博弈」兩個字（客人在罵「跟博弈網站一樣」），關鍵字表會把它判成廣告。傳統 ML 需要標註資料，而這個案子開工時一筆都沒有。LLM 讀得懂語境，且情境的判斷說明可以用自然語言迭代，正是這個階段最需要的可調整性。

代價是輸出不穩定、要處理額度與失敗。這些都在程式端接住（見下）。

### 情境群組決定下游查什麼

| 群組 | 下游工具 | 情境 |
|---|---|---|
| 訂單查詢 | 訂單系統 REST API | `order_status` `booking_change` `cancel_refund` `payment_billing` |
| 知識查詢 | 知識庫檢索 | `product_info` `policy_terms` `travel_docs` `pre_trip_info` `special_request` |
| 會員系統 | 會員 API | `member_account` |
| 不查系統 | 無，走 SOP | `service_issue` `force_majeure` `ask_clarification` `out_of_scope` |
| 轉其他單位 | 工單系統轉單 | `non_support` |
| 不受理 | 無 | `spam_fraud` `test_noise` |

CSV 的 `tools` 欄位就是這個對應的結果。PoC 只標不呼叫：訂單 API 的權限還沒核准，知識庫版本混亂，這兩件事沒到位之前接上去只會產生看起來有答案的錯答案。

### 個資邊界

法務的限制是客戶個資不得傳到未簽約的外部服務，而分類要用外部 LLM。做法是四步：

1. **本機抽取**。`triage/pii.py` 的抽取層介面是「呼叫一個本機模型服務」，PoC 用人工標註的結果模擬它的回應。標註沒涵蓋的工單直接抛例外，由上層轉真人，不猜也不放行。
2. **假名化**。原值換成同型別的假值，真實姓名換成另一個自然的姓名，手機號換成另一支格式合法的手機號。用假名而不是 `<PII_NAME_1>` 這種佔位符，是因為模型要靠語氣判斷客訴，佔位符會把文字的自然度破壞掉。理由見 `../docs/adr/0001-*`。
3. **只送假名化後的內容**。送出去的字串只能從假名化的結果組出來，對照表是處理過程中的區域變數，不寫檔、不進日誌、不進請求。
4. **寫出前還原**。草稿用假名組好之後才換回原值。`triage_result.csv` 的 `reason` 欄位保留假名（那是機器產物），`drafts.md` 是要送給客戶的，才還原。

值之間的相似關係也會保留：TK-1028 的兩個護照英文名只差一個字母，TK-1010 的錯誤與正確統編只差最後一碼。換成兩個毫不相干的假值，客戶真正的問題就在假名化的時候被消滅了。有測試守著這件事。

### 分流規則

六條，任何一條成立就轉真人。全部在程式端判斷，模型的輸出只是其中一項輸入。

| 規則 | 觸發條件 |
|---|---|
| 情境需人工 | 情境目錄登記 `requires_human` |
| 客訴性質 | 模型判定這封信在責難本公司 |
| 非客服來信 | 承辦歸屬是 `referral` |
| 不可逆動作 | 情境登記 `irreversible`，或模型判定訴求涉及退款、變更訂單、開立文件、變更帳號 |
| 殘留個資 | 假名化之後仍偵測到個資 |
| 信心不足 | 模型信心低於 0.6 |

外加降級：分類服務不可用、回應不合 schema、三層對帳矛盾、本機抽取層無法涵蓋，一律轉真人，不退回關鍵字比對。

判為不受理的工單也要過同一組規則：**只有六條全部沒成立才自動關單**，否則改成不回覆但進人工佇列。

**金額不在這六條裡面。** 工單裡的金額是客戶自己打的字，不是系統值，拿它當簽核門檻等於讓客戶自己決定要不要送簽核。所有不可逆動作一律轉真人，金額只記錄在 `money_mentioned` 欄位供人工參考。理由見 `../docs/adr/0002-*`，有回歸測試守著。

### 回覆型態與分流是兩件事

| `reply_mode` | `route` | 意義 |
|---|---|---|
| `none` | `auto` | 不回覆，自動關單 |
| `none` | `human` | 不回覆，但由人工確認該不該關單 |
| `template` | `auto` | 送出情境範本，可結案 |
| `template` | `human` | 先送出範本並告知會轉專人，案件仍進人工 |
| `ack_only` | `human` | 只回收件確認，不碰內容 |

第二列是安全閥：**自動關單是這條管線唯一會讓工單消失的動作**，所以只在完全沒有疑慮時才做。判成廣告但信心不足、或假名化後還偵測到個資，就走這一列，不回覆但交人工確認。少了它，模型只要把一封寫得很糟的真實客訴判成廣告，那封信就無聲消失了。

第四列是重點：客戶在幾分鐘內收到一個說得出內容、但不做任何承諾的回覆，案件照樣排進人工佇列。首次回覆時間降下來是這個案子的主要賣點，而讓 AI 全權回覆是客訴的來源，這一列同時處理兩件事。理由見 `../docs/adr/0004-*`。

草稿寫出前會掃一次禁用詞（金額、「已為您辦理」「將於 X 日」「同意退款」這類句式），命中就降級成 `ack_only`。這條放在程式而不是 prompt 裡，因為「不亂承諾」的失敗成本是客訴，不能建立在模型每次都聽話的假設上。

### 額度與節流

**每分鐘 15 次是這個模型免費層的硬限制，48 筆工單因此至少要跑 3 分半。** 這是設計的前提，不是可以優化掉的東西：一次呼叫處理一封工單（見上），所以 48 筆就是 48 次呼叫，額度用完就只能等視窗滑過去。

- 本機用滑動視窗自己先守住，任意 60 秒內不送出超過 15 次。額度滿了就延遲送出，直到最舊的那次請求滿一分鐘為止。
- 節流器的視窗只存在於單一行程內。換一個行程重跑（例如分批跑）時，上一批剛用掉的額度它看不到，所以仍然可能收到 429。這時照 API 回應裡寫的 `retryDelay` 等，通常就是一分鐘上下，等完之後把視窗重設。等額度不計入重試次數，因為那不是失敗，是排隊。
- 這代表**批次之間不要立刻接著跑**。要連續跑兩批，中間留一分鐘，或直接一次跑完 48 筆讓節流器自己排。
- 傳輸層錯誤重試 3 次（1 秒、3 秒）；回應不是合法 JSON 屬永久性錯誤，不重試，直接降級轉真人。
- 每次呼叫的原始回應都落地，含模型代號、prompt 版本、token 用量。要追某一筆為什麼被這樣分，直接看那個檔案。

正式環境不會用免費層，但這個限制值得留意的地方是：**額度是排隊不是錯誤**。把它當錯誤處理，工單就會在尖峰時被當成分類失敗大量轉人工；把它當排隊處理，只是延遲變長。旺季流量翻倍時這兩種寫法的差別會直接反映在人工接手率上。

## 開發過程中，模型實際出的錯

這些不是假設，是跑的時候真的發生的：

| 現象 | 根因 | 處置 |
|---|---|---|
| TK-1011 回傳 `confidence: 1.95` | schema 只寫 `"type": "number"`，值域只寫在 description 裡 | 加上 `minimum` / `maximum`。**只把約束寫在說明文字裡等於沒有約束** |
| 同一筆回了 65KB 的壞 JSON | 模型陷入重複輸出，schema 沒有長度上界，config 沒有輸出上限 | 加 `max_output_tokens=800`，並在 schema 上加 `maxLength` / `maxItems`。正常回應約 130 token |
| 颱風、價差等信被判成客訴 | `is_complaint` 的定義寫成「帶客訴情緒」，模型合理外推到「語氣強烈、事情急迫」 | 收緊成「有沒有責難本公司」，並在說明裡給出正反例 |
| 純政策詢問信心低於門檻 | 模型把「這題好不好回答」當成「分類準不準」 | 在說明裡點明信心評的是分類 |
| 記者採訪被填成 `disposition=reject` 卻選了 `non_support` 情境 | `reject` 的定義沒說清楚「真人寄來但不該由客服回」不算不受理 | 補上定義。這一筆是被三層對帳擋下來的，機制有效 |
| 同一筆工單連跑兩次結果不同 | `temperature=0.0` 之下 Gemini 仍非決定性 | 不是我們的 bug，但直接影響上線 Gate 要看哪個數字，見「已知限制」 |

## 已知限制

- **模型輸出不穩定。** 溫度就算壓到 0.0，同一筆工單重跑仍可能得到不同的情境或旗標。實測：迭代過程中同一份標註對到的一致數是 44 → 42 → 47 → 48，其中 TK-1009（指定艙位）與 TK-1045（加購行李）在兩次跑之間從 `human` 翻成 `auto` 又翻回來。**任何單次跑出來的百分比都不該當成穩定值；上線 Gate 應該看多次重跑的分佈，而不是一次的數字。** 這也是為什麼分流規則全部放在程式端：模型抖動只會影響情境標籤，動不到「發票一定轉真人」這種結論。（溫度最後設 0.1 而非 0.0，理由見下。）
- **溫度不設 0。** 完全的貪婪解碼會讓模型有機會鎖進重複輸出的迴圈，實際發生過一次回了 65KB 壞 JSON。設 0.1 足以跳出來，代價是重跑的差異略增，而上一條已經說明那個差異本來就存在。
- **本機抽取層是模擬的。** 用人工標註取代本機模型，涵蓋範圍就是這 48 筆。第 49 筆會直接轉真人。正式環境要換成真的本機模型，介面不變。
- **沒有知識庫。** 草稿內容是情境範本，是模擬的，不是任何旅行社的真實規定。要讓 `template` 的回覆真的有資訊量，前提是知識庫治理先做完。
- **沒有接任何後端系統。** 訂單 API、會員 API、知識庫檢索都只在 CSV 的 `tools` 欄標記，不呼叫。
- **證件日期沒有假名化。** TK-1018 的護照效期是判斷的依據（剩不到六個月），換掉會讓分類失去意義。這是刻意留的缺口，正式環境要靠日期偏移而不是替換來處理。
- **不做重複來信合併。** 理由見上。
- **只用 48 筆樣本。** 情境分佈、需人工比例都建立在這 48 筆上，不足以外推到每天 350 件、旺季翻倍的實際流量。

## 如果要進正式環境，接下來最重要的三件事

1. **把本機個資抽取層換成真的模型，並量它的召回率。** 現在整條個資邊界的強度等於人工標註的完整度，而正式流量不會有人先標好。這件事沒做完，法務那條限制就只是紙上的。做法是拿歷史工單做標註集，量漏抓率，把漏抓率當成上線 Gate 的一票否決項。
2. **知識庫治理先於知識庫接入。** 資訊部窗口說文件散在 Word、Excel 和一個沒人維護的舊 FAQ，版本很亂。在這個狀態下接 RAG，AI 會很有自信地引用過期的退費規定，而客戶讀不出那是舊的。要先有單一來源與版本標記，再談檢索。
3. **建立分流品質的持續量測，而不是一次性驗收。** 模型會漂、供應商會改版、情境定義會被改。需要一組固定的回歸樣本每天重跑，看情境分佈與轉真人率有沒有偏移；並且讓客服在工單系統上可以一鍵標記「這封分錯了」，讓錯誤回到樣本集。沒有這套機制，上線第一週的好數字撐不到第二個月。
