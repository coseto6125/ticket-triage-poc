# 回覆型態與分流是兩個正交欄位

作業要求 `route` 只能是 `auto` 或 `human`。但這個二值欄位表達不了我們真正想做的事：**先給客戶一個有內容的回覆，同時這件事仍然交給真人**。所以我們另立一欄 `reply_mode`，與 `route` 正交。

| `reply_mode` | `route` | 意義 |
|---|---|---|
| `none` | `auto` | 不回覆，自動關單 |
| `none` | `human` | 不回覆，但由人工確認該不該關單 |
| `template` | `auto` | 送出情境範本，可結案 |
| `template` | `human` | 先送出範本回覆並告知會轉專人，工單仍進人工 |
| `ack_only` | `human` | 只回收件確認，不碰內容 |

第二列存在的理由與第三列一樣重要：**自動關單是這條管線唯一會讓工單消失的動作**。判成廣告但信心不足、或假名化後還偵測到個資時，不能回覆（那等於回信給廣告寄件者），但也不能就這樣關掉，因為它可能是一封寫得很糟的真實客訴。不回覆而進人工佇列是唯一不會造成不可逆損失的選項。

## 為什麼值得多一欄

首次回覆時間從 6 小時降下來是這個案子的主要賣點，而讓 AI 全權回覆是客訴的來源。第三列同時解決兩件事：客戶在幾分鐘內收到一個說得出內容、但不做任何承諾的回覆，工單本身照樣排進人工佇列。

只用 `route` 二值的話，「回了多少」變成不可觀測，任務成功率就算不出來：無法區分「AI 真的解決了」和「AI 只是回了個罐頭」。

## 不承諾是程式規則，不是模型自律

範本寫檔前會掃一次禁用詞（金額數字、「已為您辦理」「將於 X 日」「同意退款」這類承諾句式），命中就自動降級成 `ack_only`。這條規則刻意放在程式而不是 prompt 裡，因為「不亂承諾」的失敗成本是客訴，不能建立在模型每次都聽話的假設上。
