# 三層判定在同一次呼叫完成，並與情境目錄互相對帳

受理判定、承辦歸屬、服務情境三層，由**同一次** LLM 呼叫以單一 JSON schema 一次輸出，三層各自是獨立欄位。程式收到之後，拿情境目錄裡每個情境登記的受理判定與承辦歸屬，去核對模型自己填的那兩欄，對不上就當作分類失敗、轉真人。

## 為什麼不是模型選一個情境、其餘查表填

查表填不可能不一致，看起來更安全。但那等於放棄了一個免費的檢查點：模型如果把一封博弈廣告判成「受理／客服」卻同時選了 `spam_fraud` 情境，這個矛盾本身就是「模型這次沒讀懂」的訊號，而查表會把訊號抹掉，留下一個看起來很乾淨的錯誤答案。

讓模型三層都答，我們就有了一個不需要標註資料就能運作的自我對帳機制。矛盾率還可以直接當成上線 Gate 的觀測指標。

## 為什麼不是三次呼叫

三次呼叫可以讓每層各自重試，但每分鐘 15 次的額度會被吃掉三倍，而且後兩層看到的是前一層的結論而非原文，錯誤會沿著鏈條放大。一次呼叫也讓「一封工單一次判斷」這件事在成本與延遲上都可預測。

## 服務情境是複數

一封工單可以同時屬於多個情境：颱風要延期又問退費，是不可抗力加上取消退費兩件事，下游要查的東西也不同。所有被選中的情境必須在受理判定與承辦歸屬上一致，否則同樣視為分類失敗。
