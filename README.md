# 工單分流

一家旅遊電商的客服工單分流 PoC。系統讀進客戶來信，判斷這封信要不要處理、該由誰處理、客戶想要什麼，然後決定它可以自動回覆還是必須交給真人。

## 目錄

| 路徑 | 內容 |
|---|---|
| `poc/` | 可執行的分流管線、測試、輸出 |
| `poc/README.md` | 執行方式、設計取捨、已知限制 |
| `CONTEXT.md` | 語彙表。討論這個系統時用哪些詞、每個詞指什麼 |
| `docs/adr/` | 幾個不明顯的決策，以及當初為什麼不選另一條路 |
| `requirements/` | 題目與原始工單資料 |

## 快速開始

```bash
cd poc
cp .env.example .env       # 填入 GEMINI_API_KEY；沒有金鑰也能跑，見下
uv run python -m triage
```

沒有 `.env` 或沒有金鑰時，管線改讀 `poc/data/responses/` 裡既有的模型回應，產出同一份結果。詳見 `poc/README.md`。

## 設計摘要

分類分三層，由同一次 LLM 呼叫一次輸出：

1. **受理判定** 這封信要不要進客服流程
2. **承辦歸屬** 受理後由客服承辦，還是轉其他單位
3. **服務情境** 客戶要的是什麼，可以同時屬於多個

情境是資料不是程式碼：`poc/triage/catalog.py` 是唯一的定義處，送給模型的說明、輸出 schema 的 enum、下游工具綁定、回覆範本全部由它生成。

個資在本機抽取後換成同型別的假值才送出，回覆寫出前再由程式換回來。分流規則六條，全部在程式端，模型的輸出只是其中一項輸入。
